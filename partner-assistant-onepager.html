Product shape

Not a generic chatbot. A local support and documentation stack.

The assistant is built for controlled technical support: run it locally, feed it the documentation you trust, restrict what each role can see, and keep the answer-to-document workflow inside the same system.

🏠

Local Tier-1 support

Deploy on a customer-controlled server with local LLM runtime. Sensitive support knowledge can stay inside the customer environment.

Role-aware knowledge

Anonymous, client, support, redactor, and administrator roles get different documentation visibility and different tools.

Technical writer built in

The same answer can become a Markdown guide, be edited in the docs workspace, published, or exported as a presentable PDF.

Ingest Index, ingest, and version existing documentation from Markdown and HTML exports.
Retrieve Search trusted manuals, custom pages, instructions, screenshots, and source metadata.
Generate Recombine retrieved evidence into practical guides for real operational scenarios.
Publish Open generated answers in docs, polish them, publish pages, or export them as PDFs.

Model-flexible by design

  • Works with OpenAI-compatible local model servers such as LM Studio.
  • Usable from Qwen 3.5 4B/9B-class models for smaller installs.
  • Answer quality scales with stronger models such as Qwen 3.6 35B or dense 27B-class setups.

Portable to other domains

  • Luxriot EVO is the current corpus, not a hard dependency.
  • A customer can bring their own documentation and run the same stack.
  • Prompts and role templates are editable from the UI, so the assistant can become Tier-1 for another domain.

Engineering controls remain visible

  • Retrieval profiles, model settings, prompt templates, ingest paths, and docs style are operator-controlled.
  • Debug views expose what was retrieved instead of hiding answer quality behind a black box.
  • Eval and telemetry hooks turn partner failures into concrete backlog items.

Working loop

From answer to maintained documentation.

The practical value is not just chat. The assistant can draft a guide, move it into the documentation workspace, let a human correct the details, then publish or export it.

1
Ask a support questionA partner asks something operational, for example: “connect an ONVIF camera and show it in Monitor”.
2
Retrieve the evidenceThe system pulls relevant indexed sections, screenshots, citations, and role-allowed custom pages.
3
Draft the guideThe model combines the sources into a scenario-specific answer instead of copying one manual page.
4
Open in docsThe answer can be opened as Markdown in the built-in documentation editor.
5
Polish and approveA redactor or support specialist fixes wording, screenshots, warnings, and structure.
6
Publish or exportThe result becomes a documentation page or a clean PDF for a partner/customer handoff.

Access model

One assistant, different information boundaries.

Role separation is part of the product, not an afterthought. The same local system can expose a limited public assistant, a client support assistant, an internal support console, a redactor workspace, and administrator controls.

Anonymous
  • Ask documentation-grounded questions.
  • Read and search public documentation.
  • See citations and relevant screenshots.
  • No saved chat history by default.
  • API/internal docs are hidden by default.
Client
  • All anonymous capabilities.
  • Login identity and saved chat sessions.
  • Client-facing home cards and documentation access.
  • Restricted from support/admin tools.
  • Web tools remain disabled by default.
Support
  • Full documentation visibility, including internal/API docs.
  • Retrieval debug and support telemetry views.
  • Can use richer support context than client roles.
  • Can edit/request publication when granted docs permissions.
  • Designed for supervised partner issue triage.
Redactor
  • Documentation reader, editor, and annotation workflow.
  • Create guides and sections, upload assets, edit pages.
  • Prepare PDF exports and request publication.
  • Can turn support answers into maintained docs.
  • No user or system administration by default.
Administrator
  • Manage users, roles, prompts, models, and retrieval settings.
  • Start ingest/reindex jobs and version documentation.
  • Approve or reject publication requests.
  • Full documentation edit, export, delete, and exclusion controls.
  • Controls the business layer on top of the assistant.

Engineering bones

The architecture is part of the value.

This is deliberately not flattened into a black-box SaaS pitch. Partners should see that the system is inspectable, configurable, and portable across documentation sets and local model choices.

Documentation pipeline

  • Markdown and HTML ingest.
  • Versioned indexes and custom published pages.
  • Screenshot extraction, source references, and broken-image reporting.
  • Repair-oriented metadata for missing or moved assets.

Retrieval and answer layer

  • BM25 profile tuned for demo reliability.
  • Embeddings and reranking available when the local machine can support them.
  • Session-aware follow-up retrieval.
  • Role-aware prompts and source filtering.

Operator surface

  • Prompt templates editable in the UI.
  • Model, retrieval, ingest, docs style, and publication controls.
  • Telemetry and debug views for real failure analysis.
  • Admin-managed home cards and guided entry points.

Roadmap

From Luxriot preview to reusable support intelligence.

The next steps turn partner feedback and support correspondence into structured knowledge, then make documentation creation increasingly assisted rather than fully manual.

Controlled access

  • Add OAuth and prepare controlled partner access.
  • Package installation, first launch, model setup, and hardware profiles.
  • Index fresh EVO 1.33 documentation and keep version switching explicit.

FAQ ingest pipeline

  • Import support correspondence, client feedback, and existing answer bases.
  • Cluster repeated issues by topic, product area, and intent.
  • Draft FAQs and focused guides from the clusters for human review.
  • Explore LoRA-style adaptation for tone, terminology, and correction patterns.

Documentation co-pilot

  • Describe a feature in a few words, then click through the software.
  • Capture screenshots and UI states from the workflow.
  • Draft a structured guide with steps, cautions, prerequisites, and images.
  • Review, publish, and feed the new document back into the assistant.
